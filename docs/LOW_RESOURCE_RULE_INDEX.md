# 大规则导出的单次调用索引

[405 准确基线](LOW_RESOURCE_405_BASELINE.md)的 1000 节点 / 大规则导出批次使用约 97.917% 单核，512 MiB 备份触顶。它完成严格功能合同，但没有证明低资源总目标。助手本地 profile 把其中的 CPU 热点定位到规则覆盖扫描：大规则每次约 170 万次 `_covers`，另有 YAML 序列化开销。

本轮只把 `build_rule_plan` 的重复扫描换为每次调用的类型精确集合、域名后缀查询及按需反转域名排序表。规则和 DNS 输出仍按原列表顺序生成；没有跨请求缓存、没有更改归一化、策略优先级、警告、IP 精确匹配或失败不直连语义。

## 差分与草稿缺陷

`tests/fixtures/rule_plan_405b64a.py` 保留 405 的原完整 planner 函数。测试给它提供未修改的解析和常量，与新路径比较完整 sections / DNS / warnings 以及公开 Mihomo YAML 字节；覆盖父子域名和边界、大小写 / IDNA、重复顺序、IP、无效输入、种子随机组合、大规则和重复调用。IP 仍是类型和值精确匹配，不新增 CIDR 包含语义。

第一份未验 WIP `59a4e80de4f46cb03b41f8f6b55bfd92337dcfab` 保存每个域名所有祖先后缀。独立审查发现最大合法输入的真实内存放大：253 字符域名、2048 direct + 2048 proxy + 256 intranet，完整 planner 独立进程高水位增量 181.895 MiB，405 对照为 10.125 MiB。该草稿没有晋升为候选，也未触发资源 CI。

修正改为仅在反向覆盖查询时为每个 domain 保存一份反转字符串，通过二分查找和点分隔边界判断；planned 索引只查询 covers，不分配该排序表。添加后的表失效与重新查询有回归，最大合法集合的额外索引内存要求低于 8 MiB。这里的 tracing 门槛只约束索引分配，不等于整组 RSS 或资源验收。

`tests/benchmarks/compare_large_exports.py` 使用临时假 1000 节点 DB、同规则、同进程交替旧 / 新 planner、四端点完整正文摘要和语义校验；8 次每路未插桩计时与额外 profile 分开。公开的第一份 JSON 只属于已否决内存方案的 59a4e80，用于保留过程，不能当最终候选收益。

## 验收与停点

修正草稿目前只有本地差分通过；最终准确候选的全量测试、独立审查、实际包大数据 512 MiB 与必要同 head 回归必须另行记证，不能继承 405 或小规模本地结果。没有放宽 256 MiB 非稀疏日志、1000 节点、大规则、备份恢复、页容差、OOM、鉴权、真实 TLS / UUID 拒绝或清理要求。

本批停点是保持完整公开输出和安全 / 恢复语义，在真实资源合同中验证此瓶颈优化；不会新增产品功能或无限扩展测量。160 MiB 完整空载、320 MiB 安装余量、真实 512 MiB 整机、连续 24 小时和其他未验场景继续按原卡分别列明。
